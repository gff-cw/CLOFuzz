# 协议状态与内存状态的双观测模型

本文给出通用描述框架的状态语义契约。它解释两类状态怎样同时保存、何时可以建立联系、哪些证据不足以支持联系。本文没有修改 StateAFL 插桩、TLSH、状态编号、队列或在线执行器，也没有运行测试。文中的拟议契约不表示当前 C runtime 已经实现这些语义。

## 1. 先区分真实系统、协议模型和观测

设 `x` 是某个时刻目标及其环境的完整具体状态，包括进程内存、线程、内核缓冲、连接、计时器和外部服务。真实状态不能由一份网络响应或一组受跟踪的内存对象完整恢复。

协议描述定义抽象状态空间 `P`。一个名称为 `ready` 的状态表示模型作者声明的协议条件；它不等于进程中的某个整数。对真实系统的协议抽象可写为 `alpha_P(x)`，但工具通常无法直接求出这个值，只能从已观测事件历史推断一组可能状态。

StateAFL 内存状态来自受跟踪对象的快照、过滤、TLSH 和 MVP 查询。将这条观测过程写为 `alpha_M(x; N, E, H)`：`N` 是内存观测命名空间，`E` 是校准及聚类判定配置的版本，`H` 是当时的聚类参考库及其演进历史。它是经验性的观测标签，不是协议状态的标准化编码，也不是完整进程状态。

因此一般不能假设存在 `P -> M`、`M -> P` 的函数，更不能假设双射：

- 同一个协议状态可以对应多个内存标签，例如缓存、历史计数和对象生命周期不同。
- 同一个内存标签可以对应多个协议状态，例如相关区别未进入被跟踪对象、被过滤，或在当前距离阈值下没有区分。
- 相同报文在不同历史、连接或目标配置下可以产生不同结果。
- 同一个协议状态名在不同模型版本中可能表达不同条件；相同内存整数在不同聚类库中也可能表达不同快照集合。

协议模型与内存聚类发生差异时，首先得到的是“观测解释不一致”或“关系尚不确定”。不能仅凭差异判定模型错误、目标实现错误或 TLSH 错误。

TLSH 距离阈值下的“足够接近”也不能直接当成数学等价关系：接近关系不保证传递性，而近邻选择还受参考库影响。协议抽象的状态划分与内存近邻标签不应共用“等价类”这一强语义。

## 2. 三种协议状态信息必须分开保存

| 信息 | 含义 | 能否作为已观测事实 |
| --- | --- | --- |
| 预测状态 | 假定请求及后续响应按描述发生时，模型推导出的结果 | 不能 |
| 候选状态集合（belief） | 与当前可见历史及已声明观测假设一致的一组状态 | 可以记录为有条件推断，不能拆成多条确定事实 |
| 确认状态 | 完整、可解释且满足所需因果关联及模型条件的既有证据足以支持的单个抽象状态 | 只能在该模型、会话与观测边界内确认 |

“确认”确认的是模型对观测的解释，不能据此保证整个目标内部实现符合标准。即使候选集合只有一个元素，也必须保留来源、完整性和关联证据；只有输入预测，没有观测证据的单元素集合仍是预测。

还应区分以下结果：

- `unobserved`：没有足够观测，不知道应处于哪些模型状态。
- `unknown`：有观测，但当前模型无法解释，或存在未解决的歧义。
- 非空候选集合：能解释，但暂时存在多种解释。
- 空候选集合：当前事件历史与所采用的模型和观测假设不相容。它不能被改写为初始状态或当成成功。

名字为 `pending` 的协议模型状态与“有一个未完成事务”的观测元数据也应区分。后者可能存在于多个协议状态中，不应隐式占用一个统一的协议状态编号。

## 3. 用有证据的多对多关系联系两类状态

只对可证明属于同一逻辑边界的观测，记录关系：

```text
R[model_digest, memory_namespace, calibration_epoch]
  contains (confirmed_protocol_state, memory_state_id, evidence_reference)
```

`R` 是有限观测样本形成的关系，不是协议状态与内存状态之间的等价证明，也不是完整笛卡尔积。出现 `(p, m1)` 和 `(p, m2)` 是允许的；出现 `(p1, m)` 和 `(p2, m)` 也是允许的。保留原始证据后才能区分模型粒度差异、内存聚类差异和不可重复观测。

有候选集合但没有确认状态时，应保留“候选集合 + 内存观测”这条不确定记录，不能把集合的每个元素都计为已确认的关系。没有可信边界时，两类记录分别保存；不为它们补造关系。

这个契约解决的是信息归属、命名与因果解释的冲突。它不保证由有限观测恢复出真实系统全部状态，也不保证聚类在数学上等价于协议抽象。

## 4. 共同边界比两个数组长度相同更重要

协议解码通常以“完整报文、事务或会话事件”为边界；StateAFL 内存快照以目标侧 I/O 跟踪的迭代边界采集。它们可能相近，也可能完全不同。下列关系都不成立：

```text
第 i 条请求 = 第 i 个响应 = 第 i 个内存标签
相同时间戳 = 相同逻辑事务
接收了一次 TCP 数据 = 收到了一个完整协议响应
发送成功 = 目标已处理成功 = 目标已静止
```

建立确定关系至少需要生产者提供共同的 `observation_id`，并明确说明这个编号如何对应双方观测。只给两个来源重复填写同一个字符串不构成证明。还需要可追溯的完成边界证据，及目标状态取样的静止性或等价同步保证。

这里的“静止”应由具体观测机制声明：取样边界覆盖哪些线程、哪些异步工作已完成、哪些外部变化仍可能发生。完整相关响应本身不证明目标进入全局静止；时钟时间接近或任意固定等待也不能替代此证据。

如果生产者只知道同一运行中的先后顺序，应记录先后或区间关系，标为未对齐，不把它升级成确定的状态对。

## 5. 各类事件的解释边界

| 既有事件 | 能支持的信息 | 不能自动推断的结果 |
| --- | --- | --- |
| 请求已完整发送 | 已发送字节与本地发送结果；事务可处于未完成状态 | 目标已经接受请求或完成响应边 |
| 完整响应且关联唯一 | 本模型可解释的响应观测；若条件充分，可确认模型状态 | 全局静止、其他事务完成、全部内部状态正确 |
| 分片或未完成帧 | 已接收的片段及解码进度 | 完整响应或成功状态转换 |
| 超时 | 在给定观测窗口内未取得所需证据 | 目标没有处理、连接已重置或协议已回到初始状态 |
| 未匹配响应 | 存在无法唯一关联的观测 | 归入最近请求并更新确认状态 |
| 显式连接关闭 | 某传输连接结束 | 进程、全局缓存、外部资源已全部重置 |
| 目标进程重启 | 新进程实例及生命周期边界 | 外部设备或持久化状态恢复默认 |
| 显式重置且后置条件已观测 | 在声明范围内建立新的重置 epoch | 超出声明范围的全局恢复 |

对于流水线、并发事务或异步通知，只有请求次序不足以决定响应归属。应保存关联键、连接与事务作用域、歧义候选及已完成状态。无法关联时可以继续保留事件，但不能污染其他事务的确认状态和缓存解释。

通用模型不能要求每种状态转换都有请求/响应对。单向协议、异步通知和已观测的初始化可以采用不同事件，但描述必须说明足够的观测条件及作用域。对于声明需要响应的事务，完整且唯一关联的响应是必要证据；对于其他事件，不能以本地发送成功代替目标侧条件。离线分析器未支持的事件应保留为未确认，不应被强行适配成伪造响应。

会话状态、连接状态、事务状态及进程级共享状态不能放在一份无作用域的 `current_state` 中。某连接关闭时只结束对应作用域；进程级内存标签仍由进程及聚类命名空间标识。

## 6. 当前代码事实及尚不存在的保证

以下是本次静态阅读得到的代码事实，不是运行测试结果：

1. 目标侧 `net_send()` 在跟踪器由 `RECEIVING` 转到 `SENDING` 时调用 `tracer_dump()` 并增加迭代计数。连续发送或连续接收不一定各产生一个快照。见 [内存跟踪器](../llvm_mode/afl-llvm-rt-state-tracer.o.c#L1112)。
2. dump 对跟踪的分配记录复制数据；结束分析阶段再过滤临时对象及 I/O 区域、计算 TLSH 并查询聚类。见 [dump](../llvm_mode/afl-llvm-rt-state-tracer.o.c#L989)、[结束分析](../llvm_mode/afl-llvm-rt-state-tracer.o.c#L1495)及[过滤](../llvm_mode/afl-llvm-rt-state-tracer.o.c#L1642)。这些操作本身没有证明协议事务与多线程目标全局同步。
3. 共享内存只保存 `seq_len`、状态数组和 `iterations`，没有协议消息、事务或共同观测编号。见 [state_shared](../llvm_mode/state-tracer.h#L23)。因此当前原始共享内存产物不足以构造逐消息的确定双状态关系。
4. `extract_response_state_tracer()` 直接复制整个共享状态序列，未按调用者传入的响应字节前缀截断序列。原 region 注解及 M2 选择使用现有响应/region 注解机制，不能把这套历史关联当成新增通用协议状态的一一对齐证明。见 [提取](../afl-fuzz.c#L3010)、[region 注解](../afl-fuzz.c#L595)及[M1/M2/M3 选择](../afl-fuzz.c#L7139)。
5. 协议 runtime 的 `semantic_step()` 可以沿声明响应边进行模拟；`proto_set_prefix()` 使用它推导 M1 后的起点。该状态属于预测信息。见 [前缀模拟](../protocol_runtime.c#L564)。
6. `proto_before_send()` 和 `response_frame()` 都可能更新同一份 `semantic_state`；这个整数混合了请求边和响应边的运行时推进，未单独编码本文件所定义的预测、候选集合和确认凭据。见 [发送前处理](../protocol_runtime.c#L506)及[响应处理](../protocol_runtime.c#L518)。不能直接把统计文件中的这个整数升级为确认状态。
7. 当前 `proto_session_begin()` 清空协议缓存并设置初始状态；网络执行入口会调用它。这是本地解释器生命周期行为，不能单独证明目标及外部状态完成对应重置。见 [会话初始化](../protocol_runtime.c#L495)和[网络入口](../afl-fuzz.c#L1490)。
8. 校准决定 MVP 距离半径，跟踪器还可能调整该半径；聚类树与计数持久化在输出目录。配置改变或聚类库重建之后，同一整数不能跨版本解释为同一观测类。见 [聚类查询](../llvm_mode/afl-llvm-rt-state-tracer.o.c#L1401)、[持久化库](../llvm_mode/afl-llvm-rt-state-tracer.o.c#L1529)及[阈值调整](../llvm_mode/afl-llvm-rt-state-tracer.o.c#L1839)。

这意味着本轮可在独立离线模块中落实上述记录和关联约束，但不能声称当前在线 C runtime 已完成双状态同步。

## 7. 命名空间、版本与生命周期

协议侧至少以模型内容摘要区分语义；只使用 `protocol_id` 不足以区分修改过的 guard、字段或状态含义。记录的摘要应覆盖所有影响解释的描述及解释器契约版本。

内存侧的 `memory_namespace` 至少应能追溯目标二进制、插桩/运行时版本、对象过滤及快照策略和聚类库身份。`calibration_epoch` 区分距离配置或判定规则的变化；聚类库重建、重新编号必须建立新的命名空间或版本。参考库追加或参考集合变化应保留当时的库修订来源，不能假定新增近邻不影响后续查询。文件路径和一个可重用的数字不能替代内容及配置来源。

`run_id` 区分独立运行，`session_id` 区分协议作用域，`session_epoch` 区分该作用域的重建。它们不替代进程身份；多个连接可能共享同一进程内存。若输入来源没有这些信息，应标记缺失，不能从文件名、记录序号或协议状态名推测补全。

关系统计若需要汇总，至少应按模型摘要、内存命名空间与校准 epoch 分区。当前 C 报告逐事件保存 library_revision、run_id、session_id、session_epoch 及原始边界来源，不执行分组或跨运行汇总。后续比较必须保留这些身份，不能把前一运行的最后状态当成下一运行的初始状态。

## 8. 离线分析器的最小记录契约

记录是对已有事实和证据的描述，不负责发送请求、执行状态转换或替生产者证明同步。分析器应拒绝未知字段、错误类型和资源超限输入，避免将拼写错误静默解释为默认状态。

| 字段组 | 必要语义 |
| --- | --- |
| 记录身份 | 契约版本、唯一事件编号、运行编号、会话编号及 epoch；同一作用域中的明确事件顺序 |
| 协议来源 | 模型摘要、预测/候选/确认信息的类别、候选集合、证据来源及完整性 |
| 内存来源 | 内存命名空间、校准 epoch、状态整数和采样来源 |
| 因果关联 | 请求/响应关联是否唯一，未完成、未匹配或有歧义的原因 |
| 共同边界 | `observation_id`、完成证据、静止或等价同步证据；证据来源可追溯 |
| 生命周期 | 显式连接/会话重建与重置事件，重置范围及已知后置条件 |

具体 JSON 校验、C 数据结构及报告以 [native_observation.c](../native_observation.c) 和[原生入口说明](native-inspection.md)为准。早期独立 Python 分析脚本已移除。当前 C 报告按事件保留观测，不自动聚合为跨作用域统计；在线 runtime 不直接生产上述记录。若旧产物缺少共同边界、epoch 或确认来源，记录仍应标为无法确认关联，不能补写历史事实或仅据此判定目标运行失败。

离线模块的输入生产者必须承担证据真实性。结构校验通过只表示记录满足契约，不能从一个 JSON 字符串验证实际线程静止、二进制身份或响应真实发生。

## 9. 必须保持的不变式

1. 协议状态与内存状态使用不同类型和命名空间；协议编号不写入 `state_ids`、原共享状态数组或 MVP 树。
2. 预测、候选集合和确认观测分别保存；模拟边不能自动转成响应证据。
3. 单个协议状态与多个内存标签的关系合法；反方向也合法。关系不压缩为覆盖其中一侧的字典。
4. 缺少完整事件、所需的唯一因果关联或可信共同边界时，不新增确定的双状态关系；声明需要响应的事务必须有完整相关响应。
5. 超时、解析失败与未知消息不等于初始状态，也不自动清空另一侧状态。
6. 模型、校准规则或聚类库身份变化后，不将新旧状态整数混合统计。
7. 重放历史与当前运行的证据分开；旧前缀的预测结果不能替代本次运行的会话观测。
8. 对不确定关联保留原因与原始来源；没有证据时保持未知，不能用数组下标或最近时间戳补出确定状态对。
9. 原状态反馈含义、TLSH 输入与原有队列语义不因新增协议解释器而改变。新增离线关联报告只解释观测，不重定义原结果。

## 10. 理论上能解决与仍需观测解决的部分

通过分离命名空间、区分预测与确认、保存多对多关系、限定因果边界和版本作用域，可以消除由类型混用、无依据对齐和跨会话污染造成的解释冲突。这些是架构契约，可以在没有新增运行实验的情况下定义并落实到记录结构。

具体目标是否在某边界完成处理、TLSH 是否区分了某个业务条件、某个模型是否覆盖实际异步行为，都属于观测充分性问题，不能用理论定义代替证据。当前输入没有足够信息时，正确结果就是“未对齐”或“无法确认”，而不是人为合并两套状态。
