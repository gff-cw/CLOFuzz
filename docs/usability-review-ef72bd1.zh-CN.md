# 当前版本能否直接正常使用：静态复核

日期：UTC 2026-11-03。源码基线：`ef72bd184478fd972bdd1e69bc3a887661500392`，分支 `feature/description-driven-c-engine-20261027`。本轮由启动/恢复、调度/校准、描述/语料三个 agent 与主审交叉检查；只读源码和描述文件，没有执行项目程序、测试或目标服务，也未修改生产实现。

## U01：验证清单之前，旧输出已被重排或删除（优先修复）

证据链：[main 先准备输出](../afl-fuzz.c#L11834) → [已有目录进入清理](../afl-fuzz.c#L10645) → [旧 queue 移至 `_resume`](../afl-fuzz.c#L6452) 或删除 → [regions、replayable queue、IPSM 等删除](../afl-fuzz.c#L6585) → [稍后才执行 manifest 配置验证](../afl-fuzz.c#L11902)。

触发条件是使用已有输出目录，描述内容、请求配置或清单版本不匹配，且旧目录通过既有 grace/resume 检查。此时最终虽然拒绝启动，旧输出已发生变化。非 resume 的 grace 窗口内可能删除旧 queue；resume 下 `_resume` 可保留原队列，但不能据此说所有旧产物完整保留。不是任意已有目录都会被清理：超出 grace 且不请求 resume 时会先拒绝。

解决思路：在持有输出目录锁之后、任何破坏性布局处理之前，增加只读的清单/配置/描述及目标路径预校验；成功后才清理或迁移，最后提交新 segment。主目标的 `check_binary` 同样晚于目录准备，缺失目标也应在破坏旧输出之前拒绝。不能简单前移 `manifest_init_or_resume_config`：它会追加并发布清单，而且新目录和锁此时可能尚未建立。需要明确预校验、目录准备与发布失败时的保留策略。验收应检查冲突失败前后旧文件内容及路径，而不只检查错误码。本轮未执行这种检查。

## U02：直接 fork 模式的退出等待可永久空转（优先修复）

在 `-n` 或 `AFL_NO_FORKSRV=1` 下，[run_target 直接 fork](../afl-fuzz.c#L4789)，随后[先执行网络函数，再 waitpid](../afl-fuzz.c#L4900)。但[网络函数末尾](../afl-fuzz.c#L2332)只循环等待 `kill(child_pid,0)` 返回 `ESRCH`，不回收子进程，也不检查停止/超时标志。

默认 Linux 子进程回收语义下，孩子退出后可成为本 fuzzer 尚未回收的 zombie，PID 仍存在；等待 PID 消失才能到达的 `waitpid` 无法执行。[SIGINT](../afl-fuzz.c#L10278)和[超时处理](../afl-fuzz.c#L10299)也只是标记和发送信号，不能补上回收。

触发限定：连接成功并走到该等待循环，且未走 `-F` 的提前返回。正常 forkserver 由另一个进程回收孩子，不能把本问题扩大为所有模式必现。解决思路是由唯一生命周期拥有者处理 wait/reap：直接 fork 路径让 `run_target` 回收，网络函数负责完成 I/O 并返回；forkserver 路径遵守状态管道协议。若保留非阻塞等待，应明确状态移交，避免提前 reap 后再次 waitpid。所有等待都应可响应停止和截止条件。验收需分别覆盖自然退出、`-K`、超时与中断；本轮未执行。

## U03：inline 校准失败之后没有完整生命周期（优先修复）

[校准开始](../afl-fuzz.c#L5052)递增 `cal_failed`；[新 wire/完整性拒绝](../afl-fuzz.c#L5081)跳过有效统计与清零；[调用者](../afl-fuzz.c#L5838)只特殊处理 `FAULT_ERROR`，仍保留该队列。全仓校准入口仅有初始 dry-run 和这里的 inline 调用，后续 `fuzz_one` 没有重试校准。

结果不是“无法变异”：该种子仍会[按零值 exec_us/bitmap_size 评分](../afl-fuzz.c#L8289)，但因[完成条件要求 cal_failed 为0](../afl-fuzz.c#L10062)，其 `was_fuzzed`、pending 计数等长期不结算。动态 session 值造成精确 wire 不同，或一次短暂传输失败，即可触发。普通初始校准成功时全局分母已有值，不能将此误报为新种子必然除零。

解决思路：保留真实 coverage 队列与要求校准通过才能获得分数两个事实，增加明确的待校准/有限重试/隔离或已定义降级状态；调度不得把缺少测量的0值当成高速、小 bitmap 的有效样本；pending 与完成状态需要独立且可结算。不能只清零 `cal_failed` 或伪造测量来制造成功。测试应覆盖一次拒绝后恢复、持续 session 差异及重试耗尽，并检查总分母、种子优先级和 pending，均尚未执行。

## U04：被拒绝的内存轨迹仍可影响队列排名（优先修复）

[unique_state_count 写入](../afl-fuzz.c#L1209)发生在完整性、重试耗尽和确认检查之前；[拒绝返回](../afl-fuzz.c#L1227)及[确认失败返回](../afl-fuzz.c#L1291)均不恢复旧值。后续若正常 coverage 校准成功，[update_bitmap_score](../afl-fuzz.c#L5150)会消费这个字段，并在[比较候选](../afl-fuzz.c#L3338)时优先考虑更多状态。

因此“没有登记 region 或状态图”并不能证明未确认轨迹完全未影响调度。解决思路是先在观察对象中计算，只有统一接纳成立后才提交队列字段；所有拒绝出口保留旧的可信值。验收要检查 `unique_state_count`、top-rated 和 favored 是否不受被拒轨迹改变，不只检查 IPSM 是否新增边。

## U05：速度/长度比较分支不可达

[第一条条件](../afl-fuzz.c#L3338)对状态数更少的候选直接 continue；[第二条条件](../afl-fuzz.c#L3342)又要求同一个“小于”条件成立，才比较速度乘长度。于是第二条分支不可达，状态数相同的新候选即使更慢、更长也会替换原 winner。

这是遗留调度问题，不是本轮编译错误。应先明确状态数优先还是联合评分，再实现状态数相等时的稳定 tie-break，并覆盖更少/相同/更多状态及更快/更慢各组合；不能仅凭改一个运算符就宣布方法对照可靠。

## U06：最小模板的合法请求范围与响应范围不一致

仅限 [minimal_runnable_example](../protocols/templates/minimal_runnable_example/protocol_spec.yaml#L138)：quantity 可在 CONTENT 变异中取1至125，而[响应 data 长度](../protocols/templates/minimal_runnable_example/protocol_spec.yaml#L276)固定为2。quantity=2 的正常4字节 data 响应会在[完整字段验证](../protocol_runtime.c#L782)被拒绝，pending 保留，同一次 execution 的下一条请求又被[单 pending 检查](../protocol_runtime.c#L705)拒绝。

必须限定：实际 `protocols/modbus_tcp/protocol_spec.yaml` 的响应 data 范围更宽，没有这个固定2字节问题；单记录执行结束后下一次 session 会清 pending，并非跨 run 永久卡住。最小修复可将模板 quantity 固定1；若保留1至125，应同时扩展响应大小和请求数量关联，增加双向闭环验收。`values:[1]` 不是 CONTENT 的封闭取值域，不能用它掩盖不一致。

## U07：自动生成的请求 fixture 不等于完整会话语料

[生成器](../tools/init_protocol_spec.py#L61)为每个请求各写一条 LE32 记录，未补会话前缀。现有 OPC UA `message.replay`、MMS `read.replay` 等也是单记录；但[OPC UA 图](../protocols/opcua_tcp/state_ir.json#L43)要求 HEL/ACK、OPN 后才能 MSG，[MMS 图](../protocols/iec61850_mms_tcp/state_ir.json#L55)要求建立 COTP/association 后才允许服务请求。

这些孤立后续请求在 HEAD/CONTENT 下不能形成合法完整序列；缺少多个前缀时，一次 SEQUENCE 插入也不能保证修复。不能把“包已生成、fixture 是完整 wire”解释成“整个 seeds 目录可直接用于该目标”。应交付与受控目标匹配的完整会话序列，明确哪些文件只是消息 fixture，或只选择初始状态请求。不要弱化状态图来得到通过。该问题不表示引擎永远无法从其他合法种子探索后续状态。

## U08：选择算法参数未严格校验，可导致空转

[`-q/-s` 解析](../afl-fuzz.c#L11680)仅用 `%hhu`，没有校验全字符串或1/2/3枚举。[choose_seed](../afl-fuzz.c#L1017)对其他值返回 NULL，而[选种内层循环](../afl-fuzz.c#L12014)不检查停止标志。已有有效状态进入此循环时，`-s 0` 或 `-s 4` 可无限重试；`-q 4` 静默选状态0。

这属于错误参数没有尽早拒绝，不是合法默认选择必然失效。应同时修完整参数校验，以及选种无可用结果时的有界、可中断行为。不能只改帮助文本或依赖调用者永远不输错。

## U09：相对 `-u` 路径与 `-U` 改工作目录不一致

[check_binary](../afl-fuzz.c#L10336)保留包含斜杠的相对路径；forkserver 子进程[先 chdir](../afl-fuzz.c#L4488)，然后[execv](../afl-fuzz.c#L4588)。例如 host 在原目录验证的 `./bin/vanilla`，在换到另一个工作目录后会指向不同文件位置；可能启动失败或执行不同文件。`chdir` 返回也未检查。

应在原目录验证时固定可执行文件绝对路径，并明确 argv 中其他相对资源路径的语义；工作目录切换失败应明确报告。当前采用绝对可执行路径可避开这一特定问题，但不能代替上述生命周期修复和运行验证。
